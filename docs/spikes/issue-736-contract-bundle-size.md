# Spike #736 — Contract module bundle size

**Question:** How much of the bundle is the contract-spec parsing machinery? Can apps that call only a few methods avoid it? Would a change here conflict with the typed-method-builder enhancement?

**Short answer:** The spec machinery (`src/contract/spec.ts`, `bindings.ts`, `abstract.ts`) is about **19.3 KB minified**. That is roughly a third of the SDK's own code for anyone who imports `TrustFlowClient`. The contract call functions already tree-shake well. The parser ships with every app because of one static edge: the `TrustFlowClient.createContractBinding()` method. Removing that edge saves **31% (brotli) for `TrustFlowClient` users and 22% for `@trustflow/sdk/escrow` users**. This PR adds a non-breaking first step: a `@trustflow/sdk/contract` subpath and a deprecation notice. Removing the method itself is a breaking change, so it should wait for the next major version.

## How it was measured

```bash
npm run size:report          # markdown table
npm run size:report -- --json
```

[`scripts/bundle-report.mjs`](../../scripts/bundle-report.mjs) bundles each scenario from `src/` with esbuild (minified, ESM, `platform: neutral`) and reads the esbuild metafile to see which source files contributed bytes. `@stellar/stellar-sdk`, `axios` and `zod` stay external, matching the `ignore` lists in `.size-limit.json`, so the numbers cover only the SDK's own code. The "prototype" column runs the same build with an esbuild `onLoad` plugin. The plugin strips `createContractBinding` and its runtime import from `client.ts`. Nothing in the source is changed.

## Current breakdown

| Scenario | Current min / brotli | Spec machinery | Prototype min / brotli | Saved (brotli) |
| --- | --- | --- | --- | --- |
| `TrustFlowClient` (root) | 61.4 KB / 17.0 KB | 19.3 KB (32%) | 38.0 KB / 11.7 KB | **31%** |
| `TrustFlowEscrowClient` (`./escrow`) | 72.6 KB / 19.6 KB | 19.3 KB (27%) | 52.8 KB / 15.3 KB | **22%** |
| `readContractState` (`./contract`) | 11.3 KB / 3.9 KB | 0 | 11.3 KB / 3.9 KB | — |
| `invokeContract` + `readContractState` (`./contract`) | 12.9 KB / 4.3 KB | 0 | 12.9 KB / 4.3 KB | — |
| `createContractBinding` (`./contract`) | 32.7 KB / 8.7 KB | 19.3 KB (59%) | 32.7 KB / 8.7 KB | — |

The root-entry saving (23.4 KB) is larger than the parser alone (19.3 KB). The binding also pulls in `invoke.ts`, `simulate.ts` and their helpers, which a plain `TrustFlowClient` user doesn't otherwise need.

Other contributors to the escrow and root bundles are `client.ts` (~6.4 KB), `escrow/client.ts` (~6.2 KB), `accounts/manager.ts` (~4.9 KB) and `storage/ipfs.ts` (~4.4 KB). `@stellar/stellar-sdk` still dominates the size a consumer actually ships (~280 KB brotli with dependencies for the root entry). The parser mostly reuses stellar-sdk's `xdr` code, which the app already loads, so the 19 KB above is close to the whole cost of the parser.

## Findings

1. **The functional contract API is already tree-shakeable.** Apps that call `invokeContract` / `readContractState` directly pay 4–4.5 KB brotli and include none of the parser. Per-method exports don't need restructuring.
2. **The whole cost comes from one class method.** `src/client.ts` imports `createContractBinding` at runtime so it can expose `client.createContractBinding()`. Bundlers can't drop an unused class method, so every `TrustFlowClient` import keeps `bindings.ts → abstract.ts → spec.ts`. The escrow, juror and profile clients all build on `TrustFlowClient`, so they pay too.
3. **The contract module had no public entry point.** `src/contract` was not re-exported from the root entry or any subpath. `tests/exports-resolution.test.ts` already fails on `main` for this reason. The only public way to get a binding was the client method that causes finding 2.
4. **Bindings can't be tree-shaken per method.** `SorobanContractClient` parses the full spec at runtime and binds every function eagerly (`bindMethods`). Code generated by `generateTypeScriptBindings` still extends `AbstractContractClient`, which builds a `SorobanSpec` at runtime. So typed, generated clients carry the whole parser too.

## What this PR changes (non-breaking)

- **New `@trustflow/sdk/contract` subpath** (tsup entry, `exports` map, `.size-limit.json` budget of 15 KB; currently 10.6 KB brotli). Apps can now import the standalone `createContractBinding(client, specEntries)`, `invokeContract`, `readContractState` and so on, and pay only for what they use.
- **`client.createContractBinding()` is marked `@deprecated`** and points to the standalone function.
- **`npm run size:report`** keeps these numbers reproducible.

## Recommended follow-up (breaking, next major)

Remove `TrustFlowClient.createContractBinding()`. The prototype column above shows the result: 5.3 KB brotli less for every `TrustFlowClient` user, with no change for apps that use bindings through the new subpath.

## Interaction with the typed-method-builder enhancement

These changes are compatible, provided the builder follows two rules:

- **Ship it from `@trustflow/sdk/contract`, not as a `TrustFlowClient` method.** A method would bring back the static edge from finding 2.
- **Generate per-method encoders instead of parsing the spec at runtime.** If `generateTypeScriptBindings` emitted standalone functions such as `fund(client, args, caller)`, each encoding its arguments with `nativeToScVal` and calling `invokeContract`, apps would get typed methods with no runtime `SorobanSpec`. Unused methods would also tree-shake away. A builder that wraps `AbstractContractClient` would work too, but it would keep paying the full ~19 KB.
